## 道韵乾坤 3D 八卦罗盘：新增中心下方实时方位度数读数组件

### 需求
在罗盘中心下方添加动态方位度数读取组件，把 3D 旋转角实时转二十四方位（子/癸/丑…），
且**显示文字不发生镜像翻转**。

### 新增文件
- `src/utils/bearing.ts` —— 二十四山换算纯函数 + SVG 极坐标工具
  - `getBearingReading(rawDeg, mirrored)` 返回山名/五行/阴阳/扇区/节气
  - 山心`i*15`，扇区 `[i*15-7.5, i*15+7.5)`，边界值归下一山
  - `polarPoint` / `annularSectorPath`：0° 指正上、顺时针为正
- `src/utils/bearingStore.ts` —— 角度广播 store（**关键性能决策**）
- `src/components/BearingReadout.tsx` —— 读数 HUD（DOM + SVG 图层）
- `scripts/verify-bearing.mjs` —— 51 项纯逻辑自测，全绿

### 修改文件
- `src/App.tsx`：镜像态 `isMirroredDial` 上提；`handleRotationChange` 里`bearingStore.publish()`
- `src/components/Luopan3D.tsx`：镜像开关改受控（`isMirroredDial` / `onToggleMirrorDial`）；
  导出 `MAX_DIAL_RADIUS = 7.25` 替代散落的 7.25 字面量；抽出 `applyMirrorToRings()`

### 两个关键设计决策（易被后人踩坑）
1. **不因镜像而反算读数。** 罗盘「镜像翻转文字」只翻转 ring geometry 的 UV 采样方向
   （渲染层左右翻转），**不改变** `globalMasterAngle` 的物理旋转方向。
   若对读数做 `360-x` 反算，读数会与盘面刻度对不上。读数一律用物理角。
2. **文字不镜像靠"分层"而非"补偿"。** HUD 是 DOM/SVG，完全不进入 WebGL UV 采样链路，
   所以罗盘贴图怎么镜像都影响不到它。SVG 里`rotate()` 只施加在 `<g>` 指针图元上，
   该组内**不含任何 `<text>`**，结构上杜绝文字被翻转。

### 性能
3D 引擎 ~60fps 上报角度。若走 React state → 每帧 60 次重渲染。
现方案：数字/指针角度每帧命令式写 `textContent`/`setAttribute`（零 React 渲染）；
山名单字与配色仅在跨越 15° 边界时 setState（每圈约 24 次）。
两个 effect 依赖数组均为 `[]` + `bearingStore.subscribe`，**不可**把 `angle` 放进依赖。

## 第三个请求：转速与默认朝向重设计（同日追加）

### 根因：帧率耦合的 bug
旧代码 `globalMasterAngleRef.current += 0.0012 * currentScale` 是**每帧增量**，
角速度 ∝ 刷新率。实测 60Hz 下 3.756 °/s（一圈 95.8 秒，每 3.99 秒跳一座山），
在 144Hz 屏上会快 2.4 倍 —— 同一份代码在不同显示器上转速完全不同。

### 改法：全部时间量改用「度/秒 + deltaTime」
`Luopan3D.tsx` 顶部导出三个常量：
- `ROTATION_DEG_PER_SEC = 1.0`（基准 1°/s → 6 分钟/圈，24 山各停 15 秒）
- `SINGLE_STEP_DEG = 1.0`（单步拨一齿）
- `SPEED_PRESETS`：0.25 / 1.0 / 3.0 三档
- `DEFAULT_CAM = { theta: 0, phi: 0.75, dist: 17.6 }`

**踩坑：THREE.Clock 的 getElapsedTime() 和 getDelta() 不能同帧共存。**
前者内部就是 `getDelta() + 累加`，共用 `oldTime`。
同帧先调 getElapsedTime() 再调 getDelta()，第二次 delta ≈ 0，转速直接塌成 0。
解法：只用 `getDelta()`，自己维护 `let elapsedTime` 累加器。

**顺带把所有插值也改成帧率无关**（原来全是每帧系数）：
- 惯性衰减 `*= 0.94` → `*= Math.pow(0.94, deltaSeconds * 60)`
- 通用插值 `lerp(k) = 1 - Math.pow(1 - k, deltaSeconds * 60)`，
  用于底盘沉降(0.08)、天环倾斜(0.06)、相机收敛(0.05)
- 环自转 `node.localAngle += ...` 补上 `* (deltaSeconds * 60)`
- `deltaSeconds` 必须 `Math.min(clock.getDelta(), 0.1)`，
  否则切后台后 rAF 恢复时一帧跳几度

### 顺带修的隐藏 bug
`onRotationChange` 上报的 `rotationSpeed` 原是 `Math.abs(angularVelocityRef.current)`，
而该 ref **只在手动拖拽惯性时非零，自转期间恒为 0** → 气场仪永远显示「恬淡中和」。
改为上报真实角速度（rad/s）：`Math.abs(angVel * 60) + autoAngularSpeed`。
`EnergyGauge` 的阈值同步从 0.05 降到 0.012 并对速度做归一化
（应用自身量程是 0.0044~0.0524 rad/s，旧阈值只有最快档能触发）。

### 默认朝向
`globalMasterAngleRef` 初始 0 + 相机 `theta: 0`（相机落 +Z 看向 -Z）
→ 子山（北）落在屏幕正上方。`phi` 从 1.05 降到 0.75（更俯视，文字更易读）。
`dist` 从 15.2/16.0 提到 **17.6**：15.2 实测左右两侧盘沿被裁出画面
（垂直可视高 = 2·17.6·tan20° ≈ 12.8，盘面投影 14.5·sin43° ≈ 9.9，余量 23%）。
场景初始化 `camera.position.set(0,11,15)` 同步改为按 DEFAULT_CAM 球坐标计算，
消除首帧「飞入」。

读数面板定位 `top-[58%] sm:top-[62%]` → `top-[63%] sm:top-[68%]`：
相机拉远后盘面变小，62% 会让面板正好压在太极盘心上（截图实测确认）。

### 顶栏
- `cycleSpeed()` 改为按 `SPEED_PRESETS.findIndex` 循环（按值匹配而非阈值区间，
  避免外部注入的 speedScale 掉进所有分支导致标签空白）
- 新增「拨齿 1°」按钮（`StepForward` 图标），点击自动暂停自转——
  单步语义是「我要停在这一格精调」，继续自转就失去意义
- App 侧用 `stepRequest` 计数器（0→1→2…）而非 boolean，以支持连点

### 写断言的教训（本轮踩了 3 次）
1. **档位循环方向**：`0.25 → 1.0 → 3.0 → 0.25`，从 3.0x 出发**点 1 次**就到 0.25x，

### 顺带修的既有缺陷：顶栏换行把 main 顶下去
`audit-readout-layout.mjs` 在 1024×768 下报「面板 bottom=1002 > 视口 768」。
**排查过程值得记住**：
1. 先怀疑是读数面板自己的问题 → 改底部锚定，无效
2. 探测 `offsetParent` 链，发现 `MAIN` 的 `top=341` 而非 67
3. 根因：`App.tsx` 里 `main` 写死 `h-[calc(100vh-65px)]`（假设顶栏 65px），
   但顶栏是 `flex` 无固定高度，1024 宽时 Zone1 标题 + Zone2 六项导航 +
   Zone3 五个按钮放不下 → flex 换行 → 顶栏涨到 341px → main 被整体下推 →
   所有以 main 为定位基准的 HUD 全部错位越界。

修法（`HUDTopBar.tsx`）：
- `header` 加 `h-[65px] overflow-hidden`，Zone1/2/3 全部 `shrink-0`，标题 `truncate`
- Zone2 导航从 `md:flex` 改 `xl:flex`（≥1280 才显示）
- 新增 Zone1.5 窄屏 `<select>` 模式下拉（`xl:hidden`），保证 <1280px 仍能切模式
- 「乾坤破阵 · 浑天仪」→「乾坤破阵」+「 · 浑天仪」`<span className="hidden xl:inline">`

**教训（重要）**：`h-[calc(100vh-65px)]` 这类「硬编码某个兄弟元素高度」的写法
天然脆弱 —— 兄弟一旦变高，整页定位基准就错位，而且症状表现为
「某个 HUD 越界」，很容易误判成是那个 HUD 自己的问题（我这次就误判了）。
以后审计脚本要**直接断言「顶栏高度 == main 假设的值」**，而不是等越界了才查。

### 断言假阳性：`range.getClientRects()` 与嵌套 span
量文本行数时用 `range.selectNodeContents(el)`，对 `<span>002.4</span>°` 这种
「内层 span + 外层文本尾巴」的结构，外层会拿到 3 个 rect（数字 1 行 + ° 的 2 个碎片），
被判成「3 行折行」，4 个视口全部假 FAIL。
修法：`el.childElementCount > 0` 的节点跳过行数判定（只对纯文本叶子算行数）。

## 第五个请求的收尾：1024×768 面板重叠的修复

### 症状与定位
新写的 `audit-hud-layout.mjs`（5 视口 × 14 项 = 70 项）首跑 **69/70**，唯一 FAIL：
`1024x768 罗盘读数 不压 五行八卦 — 重叠 66x63px`。

量化盒模型后看清了结构：
```
罗盘读数 l=318 r=706  ← 相对 main 全宽(1024)居中，右缘 706
右侧栏   l=640 r=1000 ← 绝对定位贴右，左缘 640
气场仪   l=24  r=227
可用中间通道 = 227 ~ 640 = 413px，读数 388px 刚好塞得下
```
**根因不是「面板太宽」，而是读数面板相对全屏居中、右栏贴右，两者在窄视口必然对撞。**

### 关键决策：压缩时绝不动刻度盘
第一反应是缩小迷你刻度盘（150→120）来省宽度。**这是错的**：
SVG 用 viewBox 缩放，缩小外层会让盘内 15.3px 的四正山名等比缩到 12px 以下，
而 `getComputedStyle().fontSize` **不变** → 审计脚本测不出来，但肉眼就是「看不清」。
典型的「脚本绿灯、用户仍不满意」陷阱。
→ 只压 padding / gap / min-w，保留刻度盘 150px：
   宽松 24+150+20+168+2 = 388px → 紧凑 16+150+12+148+2 = **328px**。

### 两处宽度都靠实测定档，不靠猜
1. **右栏**：`probe-aside-width.mjs` 遍历 360→260 逐档测高度与折行。
   - 360/340/320/300px：道历 h=320、折行 16 处，**完全一致**
   - 280px：道历 h=**344**（劣化起点）；260px：h=416、栏底 701 逼近视口
   → **300px 是「免费下限」**
2. **文字列**：`probe-readout-width.mjs` 用 Range 量每行自然宽度。
   `min-w:168px` 但最长行「二十四山 · 每山十五度」自然宽仅 **138px**，有 30px 余量
   → 降到 148px 安全（仍不折行）

最终 `xl`(1280) 分档：右栏 `max-w-[300px] xl:max-w-[360px]`，
读数 `gap-3 px-4 min-w-[148px] xl:gap-5 xl:px-6 xl:min-w-[168px]`。
1024 下间隙由 **-66px 转为 +16px**，四个视口读数面板尺寸完全不变（无副作用）。

### 教训
1. **「免费下限」要先测再定**：面板宽度不是越接近上限越好，也不是越小越紧凑。
   存在一个「再窄就折行」的拐点，必须逐档量出高度/折行数才能定位。
   用脚本遍历比手动试 6 次快，且不会漏掉中间档。
2. **SVG viewBox 缩放是字号审计的盲区**：`fontSize` 不随缩放变，
   computed 值恒定。审计脚本查不出「盘面文字被缩到 11px」。
   → 凡是审计不过、用户仍嫌小的，先怀疑是否存在这种「视觉缩放 ≠ CSS 字号」的结构。
3. **根因往往在布局关系而非元素本身**：读数面板 388px 并不「宽」，
   问题是它的定位基准（全屏居中）和别人的定位基准（贴右）冲突。

### 补测弹窗态：审计脚本自己的 4 个 bug（比被测代码更值得记）

原脚本只测默认态，而道历弹窗内的文字**从未被审计过**（弹窗里的 `text-sm`=14px 恰好达标，
所以肉眼也没暴露问题，但那是运气不是覆盖）。补测时在脚本自身踩了 4 个坑：

1. **`page.evaluate` 里拿不到 Node 侧变量**。`MIN_PX` 是模块常量，
   在浏览器上下文里引用直接 `ReferenceError` 崩掉整个脚本。
   → 必须作为参数传进去：`page.evaluate((minPx) => {...}, MIN_PX)`。
   注意**形参名和函数体里引用的名字要一致**，我第一版传了 `minPx`
   但体内仍写 `MIN_PX`，于是又崩一次。
2. **弹窗容器没有「同时具备 fixed 和 rounded」的单个 div**。
   实际结构是 `fixed inset-0 z-50`（遮罩层）> `max-w-3xl rounded-2xl`（内容层），
   两个类名分属不同元素。写成单div 匹配 → `modal` 恒为 null
   → **「未越界」这项被静默跳过，汇总却显示全绿**。
   → 修法：先找遮罩再 `.querySelector('div')` 取内容层；
   并把「没找到弹窗」显式判FAIL，绝不允许静默跳过。
3. **两个触发器实际指向同一个弹窗**。我用 `button[title*="万年图谱"]`
   当「今日详情」的入口，但那个 title 恰恰就是「图谱」按钮的 title。
   结果两个标签审计同一份内容，节点数一模一样（271/271）——
   **数字完全相同就是「测重了」的信号**，据此改用
   `button:has(> span:text-is("今日详情"))` 与精确 title 区分。
4. **审计脚本必须自带「可关闭」断言**。弹窗关不掉会污染后续所有断言，
   表现是后面莫名其妙飘红，难查。补了 `${label} 可关闭` 检查。

修正后 **82/82 通过**，两个弹窗节点数已区分（210 vs 271 @1440x900、
203 vs 264 @1024x768），证明确实测了两个不同弹窗。
新增断言：弹窗文字 ≥13px / 弹窗未越界 / 弹窗可关闭。

**教训（通用）**：审计脚本本身也会有 bug，而且**症状通常是「看起来全绿」**
（静默跳过、测重了同一份内容），不会主动报警。
所以审计脚本必须满足两条：① 找不到目标时显式 FAIL，不能 `if (found)` 跳过；
② 同一维度多次测量时**结果不应完全相同**，相同即说明测重了。
另外「最低字号达标」有时候是运气——本例弹窗内全是 `text-sm`(14px)
恰好过13px 线，若阈值是 15px 就会暴露。阈值别定得刚好等于现状。

## 请求十一：「还是没有展示完整」（891×776 截图，两个红框标注 135°巽位与 270°兑位）

### 诊断走了两次弯路，最终根因
**红框圈的不是「外框被裁」，而是 3D 铜环的金色边圈横穿盘面文字。**
把红框裁剪放大 7.5x / 11.7x 才看清：「木·立夏」「金·霜降」被一条金线横穿腰斩。

第一次误判：以为是被裁。量了盘沿/面板遮挡 → 用户窗口 891×776，**aspect 仅 1.148**
（我截图脚本固定 1600×1000，aspect 1.6，掩盖了窄视口问题）。
第二次误判：以为是贴图自身描边。裁剪纯贴图俯视图同区域确认**贴图上没有任何线** → 是 3D 物体。

真根因：改成近正俯视（phi 0.06）后视角几乎垂直向下，
6 道 ARMILLARY_RINGS 的 outerCollar/innerCollar（TorusGeometry，金色）
与盘面同心、平铺时只抬高 y=0.06 → 投影直接压在文字上。
斜俯视（phi 0.75）时它们是立体层次感来源，正俯视就成了遮挡。

### 关键结构事实（连踩两次坑才搞清，务必记住）
**盘面贴图 compassTex 挂在每一圈铜环的 ringMat 上，且 6 圈同心套叠共同拼成完整盘面。**
- ringMat.map = compassTex（6 圈共用一张）
- UV 被重写为 `(mirrorSign * x / maxDialRadius) * 0.5 + 0.5` → 每圈 UV 都覆盖全盘
- 6 圈环带：1.45~2.22 / 2.28~3.12 / 3.18~4.16 / 4.22~5.26 / 5.32~6.32 / 6.38~7.22
- basePlate 用的是 **earthBaseTex**（外圈装饰底板），**不是盘面**
→ 隐藏任意一圈都会在盘面挖出一条环带空洞。
实测「整组 visible=false」→ **盘面几乎消失，只剩空白底板和天池**（连出两张坏图才发现）。

### 最终方案（Luopan3D.tsx）
1. `showArmillaryRingsRef`：`viewMode !== 'compass'` → 非罗盘形态才显示铜环
   （「分层/元素/吐纳」不改 armillaryProgress，只靠 progress 会漏判）
2. 金边圈与枢轴销打 `userData.isArmillaryCollar = true`，每帧只切这些的 visible
   （**不能用 opacity 淡出**：collarMat 被 6 圈共享，会把环体一起变淡）
3. **环体压平**：`spinGroup.position.y` 罗盘形态 lerp 到 -0.08
   （ringMesh 自身已有 +0.06，叠加后落 y=-0.02，沉进 basePlate(-0.32)，
   让 ExtrudeGeometry 的 bevel 侧面藏住，消除残留的边缘高光线）
4. 立体形态 spinGroup 归 0，环体回到 y=0.06 正常高度

### 附带修的：相机距离自适应
`fitCameraDistance(aspect)` 替代硬编码 dist：
  垂直 2·d·tan(fov/2) ≥ 2R·margin，水平 2·d·tan(fov/2)·aspect ≥ 2R·margin，取较大者。
- VIEW_FIT_RADIUS = MAX_DIAL_RADIUS(7.25)，**不是**镜面铜环 15.02 / 底座 15.2。
  曾按 15.2 试过 → dist 退到 44.27、盘面缩成窗口 42%，更糟。外圈装饰允许轻微出血。
- 应用点：初始化（首帧就按真实容器 aspect 算）、handleResize（用户手动缩放过则不覆盖）、
  viewMode 切换（4 个视角全改成 base 的倍率 0.82~0.92）、handleWheel 缩放范围
  （原固定 [9,26] 改成 base*0.55 ~ base*1.9）。
- 吐纳 phi 0.42→0.04（否则比默认还斜，语义不成立）。

### 四个独立成因（按发现顺序）

**① 五行环纵向排版「双峰」（贴图层）**
- 极坐标径向剖面实测：五行环带内亮字率呈「峰(上半) → 谷(中部空) → 峰(下半)」双峰

- 成因：元素名 66px @y=-20（占 -56~+16）、季字 28px @y=+28（占 +11~+45），

- 修复：两行收拢 + 季字放大到 30px；改后剖面变单峰

**② `drawRingText` 的局部 y 轴方向（最贵的坑）**
- `ctx.rotate(midA + π/2)` 后，**局部 +y 指向盘心**（不是盘外）
- 推导：θ = midA+π/2，局部 +y 单位向量 → 全局 (-cos midA, -sin midA)
- 所以 `y<0` → 偏环带**外侧**（近 r2）；`y>0` → 偏**内侧**（近 r1）

  seasonY=+35 → r=397（内）。**与推导一致，但与直觉相反**

**③ `·冬至·` 超格 5% 横向越界（贴图层）**

## 请求十三：给「五行生克 / 八卦推演」补真实的画面差异

**用户原话**：「给「五行生克 / 八卦推演」补真实的画面差异」

### 根因（确认过的事实）
`viewMode` 在 `Luopan3D` 里只有 3 处消费：相机位置、`showArmillaryRingsRef`、吐纳音效。

### 实施：两个维度的差异

**维度 1 —— 相机语言（`Luopan3D` 的 viewMode effect）**

| 模式 | theta | phi | dist | 意图 |
|---|---|---|---|---|
| 天元总览 | 0 | 0.06 | base | 近正俯视，盘面正圆、方位无畸变 |
| 五行生克 | +0.2 | 0.72 | base*0.9 | 东侧斜俯视，盘面呈椭圆、能看见环带厚度 |
| 八卦推演 | **-0.36** | 0.86 | base*0.78 | 反向偏西、最低最近，三爻线才有立体感 |
| 分层透视 | 0.3 | 1.0 | base*0.82 | 原有 |
| 阴阳吐纳 | 0 | 0.04 | base*0.92 | 原有 |

两个新模式**偏转方向相反**（+0.2 vs -0.36），连镜头朝向都不同，
不会出现「切过去了但好像没变」的观感。

**维度 2 —— 盘面聚光（新增 `DIAL_HIGHLIGHTS` 规格 + 整张贴图重烘焙）**

`textureGenerator.ts` 里新增：
```ts
export interface DialHighlight {
  keep: readonly number[];        // 满亮保留的环带索引 0~5
  keepBoost?: number;             // 保留环额外提亮系数
  dimFactor: number;              // 压暗环的亮度系数
  focusElements?: readonly string[];  // 五行环内只留这些元素
  focusTrigrams?: readonly string[];  // 八卦环内只留这些卦
}
export const DIAL_HIGHLIGHTS: Record<string, DialHighlight> = {
  elements: { keep: [1, 2], keepBoost: 1.28, dimFactor: 0.3 },
  bagua:    { keep: [0],    keepBoost: 1.16, dimFactor: 0.24 },
  exploded: { keep: [0,1,2,3,4,5],            dimFactor: 0.62 },
};
createCompassDialTexture(highlight?: DialHighlight)
```

关键实现点（踩过的坑都在注释里）：
- **压暗用 `source-atop`**，不能用 `destination-out` —— 后者挖出透明会透出
  盘底 `earthBaseTex` 棕褐色，形成比原图更刺眼的异色环（同日 `drawRingBorder` 一节同款教训）。
- **按环带逐条画环形，不能画一个大圆** —— 保留环可能落在中间（elements 保留 [1,2]），
  大圆会把内圈八卦环一起保住，聚光失效。
- **提亮用 `lighter` 加法混合**，只提亮已有像素、保留 alpha、不产生透明。
- **`mat.color` 不能用** —— 那是整体乘法，会把天池/盘沿/铭文一起染暗，无法只暗某一环。
  正解是**重新烘焙整张 2048² 贴图**并替换 `mat.map`，旧图 `dispose()` 防 VRAM 泄漏。

### 额外做掉的：二级聚焦（顺手补上「选中即高亮」缺口）
- `selectedElement` → 五行模式下只保留该元素色块与字（其余五行**直接不画**，露底色最干净）
- `selectedTrigram` → 八卦模式下只保留该卦（连分隔线一起隐）
- 这两个 prop 此前**从未进入 3D 场景**（只喂给右侧面板与详情弹窗），
  属于上一轮我指出的**功能缺口**，本轮一并补上。
- `Luopan3D` 的 highlight effect 依赖数组为 `[viewMode, selectedElement, selectedTrigram]`。

### 踩到的坑（都要记）

**正解：`MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*'` 前缀。**
（这只影响本机 Git Bash；CI 是 Linux，不受影响。）

**② 全局 `.gitconfig` 里的 github 代理全是死的**
```
https.proxy                        = socks5://127.0.0.1:1080      ← 死
http.https://github.com.proxy      = socks5://<cred>@156.226.169.145:1080  ← 死
https.https://github.com.proxy     = socks5://127.0.0.1:10808     ← 死
```

`127.0.0.1:50766`（只能当 HTTP 代理，**push 会 sideband disconnect，只能读不能写**）。

`http.version=HTTP/1.1` 是必要的 —— HTTP/2 经代理推送易出现
`send-pack: unexpected disconnect while reading sideband packet`。

**③ curl 默认走系统代理，测本地服务要用 `--noproxy '*'`**

## 请求十五：部署失败「缺少 lock 文件」—— 改用 Bun

**用户原话**：「目前缺少lock文件部署失败了」

### 根因（已闭环）
CI 运行 #4/#5/#6 连续失败，**失败步骤是 `Setup Node`，不是 `Install dependencies`**：

```
JOB: build → failure
   ✓ Set up job
   ✓ Checkout
   ✗ Setup Node          ← 卡在这
   · Install dependencies
   · Build
```

原因是工作流里写了：
```yaml
- uses: actions/setup-node@v4
  with:
    node-version: 22
    cache: npm            # ★ 元凶
```
`cache: npm` 会让 setup-node 去找 `package-lock.json` 算缓存 key，
**找不到就在这一步直接报错退出**（不会走到安装步骤）：
> `Error: Dependencies lock file is not found ... Supported file patterns: package-lock.json, npm-shrinkwrap.json, yarn.lock`

### 修复（提交 0705f4d）
```diff
- - uses: actions/setup-node@v4
-   with:
-     node-version: 22
-     cache: npm
- - run: npm ci --no-audit --no-fund
- - run: npm run build
+ - uses: oven-sh/setup-bun@v2
+   with:
+     bun-version: latest
+ - run: bun install --frozen-lockfile
+ - run: bun run build
```

`bun.lock` 格式：**文本 JSONC，`lockfileVersion: 2`（Bun ≥1.2），带尾逗号**。
用 `JSON.parse` 直接读会报 `Expected double-quoted property name`；
核对脚本要先 `raw.replace(/,(\s*[}\]])/g,'$1')` 去尾逗号。

**一致性核对结果**（本次实测）：
- dependencies：package.json 11 / bun.lock 11 → 0 缺
- devDependencies：package.json 9 / bun.lock 10 → 0 缺（bun.lock 多一个 `esbuild`，是传递依赖，不影响 `--frozen-lockfile`）
- → `--frozen-lockfile` 不会因同步问题失败
