### 根因（本地完整复现）
`bun.lock` 的 `workspaces[""].devDependencies` 里记着 **`esbuild: "^0.25.0"`**，
而 `package.json` 里**根本没有 esbuild**。bun 比对后判定锁文件需变更（要删掉这条），
在 `--frozen-lockfile` 下直接报错退出：

```
bun install v1.4.2
error: lockfile had changes, but lockfile is frozen
note: try re-running without --frozen-lockfile and commit the updated lockfile
```

**排查时走过的弯路（记下来省下次时间）**：
1. 先怀疑「锁文件缺 Linux 平台原生包」→ **排除**。实测 `bun.lock` 里
   `@tailwindcss/oxide-linux-x64-gnu`、`lightningcss-linux-x64-gnu`、`@esbuild/linux-x64`
   **全都在**（bun 的文本锁文件会记录所有平台的 optional deps）。
2. 再比对「包名是否齐全」→ **看似通过**（11/11 + 9/9），差点误判为没问题。
3. **关键**：`--frozen-lockfile` 比的是**版本范围字符串（specifier）**，不只是包名。
   补上 specifier 逐项对比后才暴露 `esbuild` 这条。

→ **教训：核对锁文件一致性必须比 specifier 字符串，不能只比包名。**

## 请求十七：安装 bun

**用户原话**：「装一下bun」
（背景：项目已用 bun.lock，但本机没有 bun，本地 node_modules 是 npm 装的，与 CI 持续漂移）

### 安装方式选择（关键决策）
本机情况：
- `npm` 在 PATH 里的是 **WorkBuddy 隔离版**（prefix 指向 `.workbuddy/binaries/node/...`），装进去只对 agent 生效，用户自己终端用不到
- 系统 npm（`C:/Program Files\nodejs\npm.cmd`）的 prefix 是 `C:/Users/aling/AppData/Roaming/npm`
- 用户**持久 PATH**（从注册表读，`[Environment]::GetEnvironmentVariable('Path','User')`）里已有的用户级二进制目录：
  `.cargo\bin`、`.dotnet\tools`、`.local\bin`、`go\bin`、`AppData\Roaming\npm` …

**最终选择：装到 `C:/Users/aling/.local/bin`**。理由：
1. 该目录**已在用户持久 PATH 上** → 不需改任何环境变量（改 PATH 有弄坏用户环境的风险）
2. 该目录里已经有 `uv.exe` / `uvx.exe` / `python3.12.exe` / `skillhub` 等用户级 CLI
   → 语义完全一致，是这台机器约定的「用户级工具」位置
3. 免下载：复用上一轮为复现 CI 已下好的 bun 1.4.2 二进制（版本与 CI 的 `bun-version: latest` 一致）

**踩过的判断坑**：`echo $PATH` 里出现过 `/c/Users/aling/bin`，看起来也是个候选，
但查注册表发现它 **不在用户持久 PATH 中** —— 只是 agent 进程的临时注入。
→ **教训：判断某目录是否对用户终端生效，必须查注册表持久 PATH，不能只看 `$PATH`。**

### 执行
```bash
# bun 的 Windows 发行版 zip 里只有单个自包含的 bun.exe，无独立 bunx
cp bun.exe "C:/Users/aling/.local/bin/bun.exe"
cp bun.exe "C:/Users/aling/.local/bin/bunx.exe"   # bun 按可执行文件名分派 bunx
```

### 验证
| 检查 | 结果 |
|---|---|
| `which bun` | `/c/Users/aling/.local/bin/bun` |
| `bun --version` | **1.4.2** |
| `which bunx` / `bunx --version` | `/c/Users/aling/.local/bin/bunx` / **1.4.2** |
| `bun x --version`（子命令形式） | **1.4.2** |
| 项目内 `bun install --frozen-lockfile --dry-run` | ✅ exit 0（锁文件一致） |

`--dry-run` 是故意的：**只校验不写入**，避免把用户 npm 装的 node_modules 换掉。
已确认 `git status` 干净、`bun.lock` 未被改写。

### 收尾
- 临时下载目录 `%TEMP%\bun-dl`（40MB zip + 86MB exe）已清理
- 未改用户任何环境变量
